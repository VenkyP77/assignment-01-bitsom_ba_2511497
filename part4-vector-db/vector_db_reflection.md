## Vector DB Use Case

A traditional keyword-based database search would not suffice for this system. Keyword searches rely only on exact or partial string matching. This limits its ability to understand what a lawyer is actually asking. For example, when a lawyer queries "What are the termination clauses?", a keyword search would only find paragraphs containing the exact word "termination." However, contracts frequently express the same concept using different phrases like "conditions for ending the agreement," "early exit provisions," or "cancellation rights". THese all describe termination clauses without using that specific word. A keyword search would miss these entirely, forcing lawyers to guess every possible phrasing and run dozens of separate searches across a 500-page document.

A vector database solves this problem by storing contract text as numerical embeddings which are vector representations that capture semantic meaning rather than just words. When a contract is ingested, it is split into chunks (paragraphs or sections), and each chunk is converted into an embedding using a model like all-MiniLM-L6-v2 or a legal-domain model. These embeddings are stored in a vector database.

When a lawyer submits a natural language query, it is also converted into an embedding, and the vector database performs a similarity search (cosine similarity is popular) to retrieve the most semantically relevant chunks, regardless of the exact words used. This means "termination clauses" would match paragraphs about "ending the agreement" because both share similar meaning within the embeddings. The result is a far more accurate, intuitive, and complete search experience that understands the legal intent of the query rather than just matching keywords within it.
